# Architecture

How the project fits together, why it is shaped this way, and which numbers are
coupled to which. Read this before changing anything structural. For step-by-step
"how do I add X" recipes see [EXTENDING.md](EXTENDING.md); for *why* things are the
way they are see [DESIGN_LOG.md](DESIGN_LOG.md).

---

## 1. What the project is

A **PyBullet simulation** of a vertical farm and a robot that services it, built to demonstrate
*perception → decision → physical action* for an agentic-vision project:

* The farm is a 3 × 3 grid of vertical **poles** ("stations"). Each pole carries 4 layers of
  elongated **trough pods** on each of its two faces (72 pods), and each pod carries a row of
  3 **plants** (216 in all).
* One **machine** rides an overhead **rail network** and carries **four agents**: on each side
  of the beam a **camera agent** and a **service agent**. At each station the camera
  images and assesses every pod, and *after it has moved on* the service agent waters or
  treats the pod's plants according to the decision.
* Perception is a **stub** today (a random or mostly-correct classifier). Everything else —
  decision agent, logging, motion, coordination — is real code, so a real classifier can be
  dropped in without touching the rest.

## 2. The layers

```
 ┌──────────────────────────────────────────────────────────────────────────────┐
 │ main.py                    GLUE: the demo loop, console narration, CLI         │
 │   calls ─► assess(pod) callback ─► perception_stub ─► decision_agent            │
 │                                     (classify)          (decide, service map)   │
 │                                   ─► run_logger (one CSV/JSON row per pod)      │
 ├──────────────────────────────────────────────────────────────────────────────┤
 │ gantry_robot.py            THE MACHINE + SCHEDULER (PyBullet)                   │
 │   scene (poles, rails, troughs, plants) · rods · state readers · rail router    │
 │   generator-based scheduler · camera job · service job · public API             │
 │   ◄── loads ── urdf/gantry.urdf ◄── generated by ── tools/generate_gantry_urdf.py│
 ├──────────────────────────────────────────────────────────────────────────────┤
 │ pod_registry.py            DATA LAYER: where every pole/trough/plant is          │
 │                            + what is "really" growing there (ground truth)      │
 └──────────────────────────────────────────────────────────────────────────────┘
   Tests:  verify_motion.py (audits gantry_robot per physics step)
           run_checks.py    (runs everything, incl. cross-file consistency checks)
```

Dependencies only point **down**: `pod_registry` imports nothing from the project;
`gantry_robot` imports only `pod_registry`; `main` imports everything; the checkers import
what they test. `decision_agent`, `run_logger` and `perception_stub` know nothing about
PyBullet — you can unit-test them in isolation.

## 3. The life of one pod (data flow)

```
  gantry_robot._g_camera            camera head slides along the pod, stopping at each of the 3 plants
        │  emits plant_scan ×3
        ▼
  gantry_robot._g_camera            emits "assess", then calls  assess(pod)   ← main.py's closure
        │
        ▼
  main.assess(pod):  load_frame ─► classify_pod ─► decide ─► service_action_for
        │                          {stage, disease, conf}   {action, reason}   "water"|"apply_treatment"|None
        │            ─► logger.log(...)            row created, service_status "pending"/"not_required"
        │            ─► robot.mark_pod_decision()  trough turns green / yellow / red
        │            ◄─ returns {"service_action", "camera_dwell"}
        ▼
  gantry_robot._g_camera            holds camera_dwell s, moves to the next pod, then sets
        │                           shared["camera_left"][side] += 1   and emits "camera_left"
        ▼                                                      │ (this releases the service agent)
  gantry_robot._g_service  ◄───────────────────────────────────┘   waits on that counter, then:
        │   if action is None: emit "service_skip"
        │   else: go to the pod's height, emit "service_start",
        │         for each plant: head in front ─► applicator out ─► "service_contact" ─► hold ─► applicator in
        │         place the coloured tag, emit "service_done"
        ▼
  main.on_event("service_done") ─► logger.mark_service(pod_id)   status "done", timestamp
```

The **only** coupling between the camera and service agents is the tiny `shared` dict created per
station in `service_station()` (`assessed[pod_id]` and `camera_left[side]`). Everything else each
agent does on its own.

## 4. The machine

### 4.1 Physical picture

* The **chassis** rides *on top of* the rail on wheels (never through it). It stops with its
  centre exactly over each pole.
* Two **outrigger rails** stand on the chassis and reach out over the aisle on both sides.
* One **drive box** per side rides on them (front box at +Y, back box at −Y). Each box holds both
  winch drives for that side (two-tone body: teal = camera bay, purple = service bay) and
  **slides toward the beam** ("disengage") for travel between poles and parking, and back out
  ("engage") to work.
* Each side has a **camera agent** (rod at x − 0.11, 0.505 m from the beam) and a **service
  agent** (rod at x + 0.11, 0.385 m from the beam). The staggered depth lets each head slide
  past the *other* agent's rod.
* An agent = a **hoist** (its rod lengthens downward) ending in a **yoke** that carries a
  **two-stage telescoping traverse**; the **tool head** hangs from the carriage at its tip. The
  traverse slides the head *along the pod* from plant to plant.
* The service agent's head has a **contact applicator**: a slim rod with a gold pad that slides
  toward the plant until it touches (~2 mm short), holds, and slides back.

### 4.2 The kinematic tree (`urdf/gantry.urdf`, 18 joints, all prismatic)

| # | Joint | Moves | Axis | Range (m) | Notes |
|--:|---|---|---|---|---|
| 0 | `carriage_joint` | the whole machine along a horizontal rail | +X | −0.5…2.5 | value = world x |
| 1 | `row_joint` | the machine along an outer vertical rail | +Y | −1.5…4.0 | value = world y |
| 2 | `box_front` | front drive box | −Y | 0…0.30 | value = how far *in* (0 = engaged) |
| 3 | `hoist_front_camera` | rod's lower end | −Z | 0…2.6 | value = how far *down* |
| 4–5 | `stage1/2_front_camera` | telescoping traverse | +X | 0…0.115 each | camera extends toward +x |
| 6 | `hoist_front_service` | | −Z | 0…2.6 | |
| 7–8 | `stage1/2_front_service` | | +X | −0.115…0 each | service extends toward −x |
| 9 | `applicator_front_service` | contact pad | toward pod | 0…0.10 | needs only 0.029 |
| 10 | `box_back` | back drive box | +Y | 0…0.30 | |
| 11–17 | `hoist/stage1/stage2_back_camera`, `…_back_service`, `applicator_back_service` | mirror of 3–9 | | | |

Chain: `base → carriage_joint → row_joint → box_<side> → hoist_<side>_<role> → stage1 → stage2 → (applicator)`.
The base is fixed at world `(0, 0, BASE_Z)`, so `carriage_joint`/`row_joint` values are simply the
machine's world x/y. Links are never rotated, so local axes = world axes.

Two conventions to remember:
* Joints are always looked up **by name** (`getJointInfo`), never by number.
* PyBullet numbers a *link* with the index of the joint that leads to it — used by
  `agent_head_position_from_link()` to read the carriage link's pose.

### 4.3 Heights (world z, metres)

| z | What |
|--:|---|
| 0.28, 0.70, 1.12, 1.54 | trough centres, layers 0–3 |
| 2.29 / 2.32 | rail centreline / rail top (wheels rest here; poles end flush) |
| 2.38 | `BASE_Z`: chassis-plate centre |
| 2.535 | `HOIST_ORIGIN_Z`: bottom face of the drive boxes = top end of every rod |
| ≈ 0.28 | lowest head position: needs hoist extension `2.535 − 0.095 − 0.28 = 2.16` (limit 2.6) |

## 5. The scene

Built in `GantryRobot._build_farm_structure()`; **everything is visual-only** (no collision
shapes). That is deliberate — see §9. Each static thing is also recorded in `robot.obstacles` as
`(name, min corner, max corner)` so the verifier can check clearances numerically.

| Obstacle name prefix | Count | What |
|---|--:|---|
| `pole` | 9 | vertical poles, top flush with the rail top |
| `rail` | 5 | horizontal rails 1, 2, 3, 4, end (the "horizontal poles") |
| `vertical rail` | 6 | the two outer vertical rails, 3 segments each (dock / rows / dock) |
| `trough` | 72 | one box per pod (recoloured by decision) |
| `bracket` | 72 | tie each trough to its pole |
| `plant` | 216 | one bounding box per plant |
| `service marker` | added at run time | the tag left on a pod once serviced |

Plants are drawn as **one link-less body per pod with a compound visual** (a port ring + a
crop-specific tuft per plant). Read the warnings in §10 before touching this.

### The rods
The rods are *not* in the URDF (a fixed-length link cannot span 0.4–2.2 m). Each is drawn from **nine
fixed tube pieces** (5 mm × 256, 128, … 1) that are only ever *moved*: for a given length the pieces
whose bits are set are stacked from the drive box down. No body is ever created or deleted during a
run, which is what keeps the GUI free of flicker. Details: `class _Rod`.

## 6. The scheduler (how four agents act at once)

There are no threads. Everything that takes time is a **generator** that `yield`s once per physics step:

```python
def _g_something(self):
    yield from self._g_settle({joint: target})   # command joints, resume when arrived
    yield from self._g_wait(0.5)                 # do nothing for 0.5 s of sim time
    yield from self._g_wait_until(lambda: flag)  # block until another task sets flag
```

`_run(tasks)` gives every live generator one turn, steps the simulation once, and repeats until all
finish. That is how the front and back sides — and, within a side, the camera and service agents —
genuinely work in parallel, and how "the service agent waits for the camera" is just a `while`
loop that yields.

Timeline of one side (camera C, service S), pods top→bottom:

```
 C: descend ── plants 0,1,2 ── assess ── hold ── move to pod 2 ─┬─ plants ── assess ── ...
                                                               └─ camera_left(pod 1)
 S:  (waits)  ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┴─ go to pod 1 ── plant-by-plant service ...
```

Blocking moves (`_settle`, `dwell`) just run one generator alone. Two safety caps: `MAX_SETTLE_STEPS`
makes a stuck joint move *give up silently* (a verifier rule will then complain about the resulting
state), and `MAX_RUN_STEPS` *raises* if a whole run deadlocks (two tasks waiting on each other).

## 7. Motion rules (the machine's safety invariants)

Enforced in `gantry_robot.py` (mostly by `assert` and by the *order* of operations) **and**
re-checked every physics step by `verify_motion.py`:

1. The chassis moves along **one axis at a time**, only **along a rail**.
2. The chassis moves only with everything **stowed**: hoists up, heads centred, applicators in.
3. The chassis moves in Y (changes pole) only with the **drive boxes slid in**.
4. A drive box slides only with everything stowed and the machine standing still.
5. Hoists deploy only with the boxes **engaged**.
6. A head slides along the pod only with its applicator **in**; the applicator slides out only while
   the hoist and head are standing still.
7. The service agent starts on a pod only after the camera has **assessed it and moved on**.

The route (`service_station`, `park_at_dock`): stow → (slide boxes in if changing pole or docking) →
drive along rails only → (slide boxes out at a station) → work → repeat. Routing lives in
`_plan_rail_route` (nearest outer vertical rail, one axis per leg).

## 8. Verification architecture

Three layers, all in `verify_motion.py` (catalogued as rules R1–R16 in its docstring):

| Layer | When | Examples |
|---|---|---|
| per step (`Checker.__call__`) | after every physics step | on rails, one axis, stowed to drive, no part within 20 mm of anything, rods steady |
| at events (`on_event`) | when a plant is imaged/touched | head level with pod, in line with the plant, boxes engaged, **URDF agrees with the constants** |
| whole run (event log) | after the run | every plant imaged before assess; right service action; every plant touched once; correct order |

The clearance check needs geometry, so `GantryRobot.robot_volumes()` describes the machine as ~41
axis-aligned boxes. **That function mirrors the URDF by hand.** If you add a physical part to the URDF,
add a box there or the check silently stops protecting it (see EXTENDING.md).

`run_checks.py` wraps it with instant checks: syntax, "URDF matches generator", **design constraints**
(the coupled-numbers table in §10, as executable checks), decision-table consistency, registry sanity,
legacy imports, and "the whole scene builds" (catches e.g. the 16-shape plant limit).

## 9. Why the scene has no collision shapes

Early on the poles had collision geometry and the carriage physically jammed against them. Now the
machine is kept clear by *routing* and the clearance is *proven numerically* every step. The
consequence: nothing stops the machine from passing through an obstacle if the routing/rules are wrong —
`verify_motion.py` is the only thing that would notice. Run it after every change.

## 10. Numbers that are coupled (change one → check the others)

| If you change… | …it is sized against… | Symptom if you forget |
|---|---|---|
| `PLANT_X_OFFSETS_M` (pod_registry) | traverse reach `2 × STAGE_LIMIT_PER_STAGE_M`; trough length `TROUGH_HALF_EXTENTS_M[0]`; agent x-offset | `run_checks` design-constraints; verifier "out of line with the plant" |
| `AGENT_X_OFFSET_M` (0.11) | straddling the outer vertical rail; both inside the 0.44 m trough; portal posts sit at the same x | rods/heads touching the outer rail |
| `BAY_OFFSET_M` (0.06) | heads must pass the other agent's rod: `MIN_AGENT_TO_AGENT_M` | verifier "agent within … of agent" |
| `BOX_REACH_M`, `BAY_OFFSET_M` | `DOCK_SPACING_M`, `ROW_SPACING_M`, `APPLICATOR_STROKE_M` | design-constraints; heads hitting dock bar or next row |
| `BOX_RETRACTED_REACH_M` (0.26) | service applicator (points at the beam when retracted) vs the portal post; heads vs the chassis plate | verifier "…within … of portal post" |
| `STAGE_LIMIT_PER_STAGE_M`, `BAR_*` | plant reach; the sleeve must stay *behind* the rod so it never crosses the outer rail's line | verifier: bars/sleeve touching the vertical rail |
| `HOIST_ORIGIN_ABOVE_CHASSIS_M`, `HEAD_DROP_M`, `RAIL_DROP_M` | pod z range (`BASE_HEIGHT_M`, `LAYER_SPACING_M`); hoist joint limit 2.6 | design-constraints (hoist reach) |
| `SERVICE_REACH_M`, `PLANT_PROTRUSION_M`, `SERVICE_NOZZLE_TUBE_END_M` | `APPLICATOR_STROKE_M` = reach − plant front − retracted tip − gap | pad not touching / pushing in (verifier contact band) |
| any dimension shared with the URDF | regenerate it: `python3 tools/generate_gantry_urdf.py` | `run_checks` "urdf-generator" fails |
| `DECISION`-related names | tables in decision_agent + `gantry_robot.DECISION_COLOR` | `run_checks` "decision-tables" |

## 11. Performance notes (learned the hard way)

* Headless the simulation runs at ≈ 0.2 ms per physics step (5,000 steps/s); a full `main.py` run is
  ~13 s. In the GUI, `--sleep 0.004` ≈ real time.
* **Multi-link static bodies are expensive**: PyBullet steps every link of every body each step. 72
  plant bodies with ~18 links each made every step ~4× slower. Use link-less bodies with a
  compound visual instead (`createVisualShapeArray`, **max 16 shapes — more segfaults**).
* **Per-step GUI drawing is expensive**: an earlier spray effect made ~12,000 `addUserDebugLine` calls
  in three stations and visibly slowed the GUI. Avoid per-step debug drawing.
* **Never delete/create bodies per step** (flicker); move existing ones.
* The solver iteration count does not matter here (no collisions).
